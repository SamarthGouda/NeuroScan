## 2. Normalization & Data Integrity Analysis

### 2.1 Normal Form Evaluation
The schema adheres strictly to **Third Normal Form (3NF)** with one intentional, controlled denormalization:

- **1NF (First Normal Form):** Every cell stores an atomic value (except serialized JSON payload columns). All tables possess a definitive primary key (`id`).
- **2NF (Second Normal Form):** All non-key attributes depend on the entire primary key, completely eliminating partial dependencies (UUID primary keys inherently avoid composite key dependencies).
- **3NF (Third Normal Form):** Non-key attributes depend solely on the primary key, with zero transitive dependencies. Patient information (`age`, `gender`, `hospital_name`) resides in `patients`, referenced by foreign key in `scans` and `cases`.

### 2.2 Intentional Controlled Denormalization
- **Denormalized Attribute:** `analyses.patient_id` is redundant because `analyses` already links to `scans.id`, which links to `patients.id`.
- **Engineering Justification:** In high-volume clinical systems, queries frequently fetch a patient's entire diagnostic history (`SELECT * FROM analyses WHERE patient_id = :p_id`). Maintaining `patient_id` directly on `analyses` with an index avoids performing an expensive two-table join across `scans` on every dashboard refresh.

### Query 1: Clinical Dashboard Aggregation Query
Executed in `backend/api/routes_stats.py:31-74` to populate physician and technician dashboard counters.

```sql
SELECT 
    COUNT(s.id) AS total_scans,
    COUNT(CASE WHEN s.status = 'completed' THEN 1 END) AS completed_scans,
    COUNT(CASE WHEN s.status IN ('pending', 'analyzing') THEN 1 END) AS pending_scans,
    COUNT(DISTINCT s.patient_id) AS total_patients,
    COUNT(c.id) AS total_cases,
    COUNT(CASE WHEN c.status = 'active' THEN 1 END) AS active_cases,
    AVG(a.confidence) AS avg_confidence,
    AVG(a.uncertainty) AS avg_uncertainty,
    COUNT(CASE WHEN a.predicted_class != 'notumor' THEN 1 END) AS tumors_detected
FROM scans s
LEFT JOIN analyses a ON s.id = a.scan_id
LEFT JOIN cases c ON s.id = c.scan_id;
```

#### Clause-by-Clause Explanation:
- `SELECT COUNT(s.id)`: Measures total scans ingested in the system.
- `COUNT(CASE WHEN ... THEN 1 END)`: Conditional aggregation pattern (mimics `FILTER (WHERE ...)` in standard SQL). Evaluates scan and case status without running separate queries.
- `COUNT(DISTINCT s.patient_id)`: Counts distinct patient entities represented across the scans catalog.
- `AVG(a.confidence), AVG(a.uncertainty)`: Computes statistical means of model certainty across all processed analyses.
- `FROM scans s LEFT JOIN analyses a ... LEFT JOIN cases c`: Left outer joins preserve scans that may have failed before analysis creation or cases that were unassigned.

#### Illustrative Output:
| total_scans | completed_scans | pending_scans | total_patients | total_cases | active_cases | avg_confidence | avg_uncertainty | tumors_detected |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 23 | 23 | 0 | 11 | 23 | 18 | 0.8984 | 0.0241 | 21 |

#### Interview Follow-Up Question:
- **Q:** *Why is `LEFT JOIN` used here instead of `INNER JOIN`?*  
  **A:** If an `INNER JOIN` were used, any newly uploaded scan currently being processed (where an `Analysis` record has not yet been committed) would be completely excluded from the row count, falsely reporting an undercount of active institutional scans.

### Query 2: High-Risk Urgent Triage Fetch
Executed when populating the physician's emergency review queue (`routes_cases.py` & `routes_scans.py`).

```sql
SELECT 
    c.case_number,
    c.priority,
    c.status,
    p.patient_code,
    p.full_name AS patient_name,
    p.age,
    a.tumor_type,
    a.confidence,
    a.risk_level,
    a.risk_score,
    s.created_at AS scan_date
FROM cases c
JOIN patients p ON c.patient_id = p.id
JOIN scans s ON c.scan_id = s.id
JOIN analyses a ON c.analysis_id = a.id
WHERE c.status = 'active' 
  AND (c.priority = 'urgent' OR a.risk_level = 'HIGH')
ORDER BY a.risk_score DESC, c.created_at ASC
LIMIT 20;
```

#### Clause-by-Clause Explanation:
- `FROM cases c JOIN patients p ... JOIN scans s ... JOIN analyses a`: Multi-table inner join pulling normalized data across 4 related tables.
- `WHERE c.status = 'active' AND (c.priority = 'urgent' OR a.risk_level = 'HIGH')`: Filters strictly for actionable cases requiring immediate radiologist review.
- `ORDER BY a.risk_score DESC, c.created_at ASC`: Dual-column ordering: highest clinical risk appears first; ties are broken by oldest scan date (FIFO triage).
- `LIMIT 20`: Restricts results to prevent UI rendering lag.

#### Illustrative Output:
| case_number | priority | status | patient_code | patient_name | age | tumor_type | confidence | risk_level | risk_score | scan_date |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| CASE-2026-0009 | urgent | active | PT-2026-9901 | Arthur Pendelton | 58 | Glioma | 0.942 | HIGH | 0.784 | 2026-03-28 14:22:01 |
| CASE-2026-0014 | urgent | active | P-1415 | Jitika Saha | 21 | Pituitary Tumor| 0.912 | HIGH | 0.691 | 2026-04-01 09:15:30 |

#### Interview Follow-Up Question:
- **Q:** *Which indexes are required to make this query execute in sub-millisecond time at enterprise scale (1,000,000 cases)?*  
  **A:** A composite B-tree index on `cases(status, priority)` and an index on `analyses(risk_level, risk_score)`. The query planner can then execute an Index Scan rather than a Sequential Table Scan across all 4 tables.

### Query 3: Multi-Filter Regulatory Audit Trail Search
Executed in `backend/api/routes_audit.py:34-69` during compliance audits.

```sql
SELECT 
    al.id,
    al.timestamp,
    al.username,
    al.role,
    al.action,
    al.resource_type,
    al.resource_id,
    al.ip_address,
    al.details
FROM audit_logs al
WHERE al.action = 'UPLOAD_AND_ANALYZE_SCAN'
  AND al.timestamp >= '2026-01-01 00:00:00'
  AND (al.details LIKE '%Glioma%' OR al.username LIKE '%doctor%')
ORDER BY al.timestamp DESC
LIMIT 50 OFFSET 0;
```

#### Clause-by-Clause Explanation:
- `WHERE al.action = ... AND al.timestamp >= ...`: Bounds the search space using indexed columns.
- `AND (al.details LIKE ... OR al.username LIKE ...)`: Implements partial keyword search across narrative details and usernames.
- `ORDER BY al.timestamp DESC`: Forces reverse chronological ordering.
- `LIMIT 50 OFFSET 0`: Implements standard offset-based pagination.

#### Performance Consideration:
- Using leading wildcards (`LIKE '%Glioma%'`) prevents B-tree indexes from performing an index range scan, forcing a partial table scan. For large-scale production logs, replace `LIKE` with PostgreSQL Full-Text Search (`to_tsvector` and `@@ to_tsquery`) supported by a GIN (Generalized Inverted Index).

### Query 4: Incremental Diagnostic Report Revision Fetch
Executed in `backend/api/routes_reports.py:74-93` when determining the next report version number.

```sql
SELECT COALESCE(MAX(version), 0) + 1 AS next_version
FROM diagnostic_reports
WHERE scan_id = '1b99e424-9988-4eed-af89-d0ab254fa6b7';
```

#### Clause-by-Clause Explanation:
- `WHERE scan_id = ...`: Scans the indexed foreign key.
- `MAX(version)`: Finds the highest existing revision number.
- `COALESCE(..., 0) + 1`: If no report exists (`NULL`), defaults to 0 and adds 1, producing version 1. If version 2 exists, returns 3.

#### Correctness Consideration:
- In high-concurrency environments where multiple doctors might edit simultaneously, this read-then-write pattern can encounter race conditions. This should be wrapped in an ACID transaction with an explicit uniqueness constraint on `(scan_id, version)` to prevent duplicate version generation.

### Problem 1: Find Orphaned Scans (Missing Foreign Keys)

```sql
-- PRACTICE QUERY 1: Detecting Orphaned Scans
SELECT
```

### Problem 2: Identify Duplicate Patient Records

```sql
-- PRACTICE QUERY 2: Detecting Duplicate Patient Entities
SELECT
```

### Problem 3: Second-Highest Risk Score Per Tumor Pathology
*Using SQL Window Functions, find the second-highest risk score recorded for each distinct tumor class.*

```sql
-- PRACTICE QUERY 3: Second-Highest Value via DENSE_RANK() Window Function
WITH RankedAnalyses AS (
    SELECT 
        predicted_class,
        scan_id,
        risk_score,
        DENSE_RANK() OVER (
            PARTITION BY predicted_class 
            ORDER BY risk_score DESC
        ) AS rank_pos
    FROM analyses
)
SELECT 
    predicted_class,
    scan_id,
    risk_score AS second_highest_risk_score
FROM RankedAnalyses
WHERE rank_pos = 2;
```
- **Interview Talking Point:** Window functions (`DENSE_RANK() OVER (PARTITION BY ... ORDER BY ...)`) are superior to subqueries because they process partitions in a single scan without Cartesian cross-products.

### Problem 5: Total Scans and Average Volume By Doctor
*Compute total scans reviewed, average confidence, and total tumor volume percentage for every doctor, including doctors who have reviewed zero scans.*

```sql
-- PRACTICE QUERY 5: Left Outer Join Aggregation
SELECT 
    u.id AS doctor_id,
    u.full_name AS doctor_name,
    COUNT(c.id) AS total_cases_assigned,
    COALESCE(ROUND(AVG(a.confidence) * 100, 2), 0.0) AS avg_confidence_pct,
    COALESCE(ROUND(SUM(a.segmentation_area_percent), 2), 0.0) AS total_tumor_volume_sum
FROM users u
LEFT JOIN cases c ON u.id = c.assigned_doctor_id
LEFT JOIN analyses a ON c.analysis_id = a.id
```

### Problem 8: Cumulative Scan Ingestion Velocity
*Using Window Functions, compute the running cumulative sum of scans ingested day-by-day.*

```sql
-- PRACTICE QUERY 8: Cumulative Aggregation via Running SUM
WITH DailyScans AS (
    SELECT 
        DATE(created_at) AS acquisition_date,
        COUNT(*) AS daily_count
    FROM scans
    GROUP BY DATE(created_at)
)
SELECT 
    acquisition_date,
    daily_count,
    SUM(daily_count) OVER (
        ORDER BY acquisition_date ASC 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_scans_total
FROM DailyScans;
```

### Problem 10: Performance Optimization: Index Analysis & Query Plan
*Given a query filtering scans by date range and archival status, write the optimal composite B-tree index and explain the `EXPLAIN QUERY PLAN` output.*

```sql
-- PRACTICE QUERY 10: Index Creation & Execution Plan
CREATE INDEX idx_scans_archived_created 
ON scans(is_archived, created_at DESC);

EXPLAIN QUERY PLAN
SELECT id, filename, patient_id

  AND created_at >= '2026-01-01 00:00:00'
```
